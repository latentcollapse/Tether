# Tether v2.1.2 — Reap no longer kills agent MCP transports

Patch fix for a regression in v2.1.1's process reaping.

## The bug

v2.1.1 added reaping to clear orphaned delivery daemons on dashboard startup. Its match
list included `tether/mcp_server.py` — but those are **not** delivery sprawl. Each agent's
client spawns its own `mcp_server.py` as a stdio transport to call `tether_receive` /
`tether_send`, and that process does not respawn mid-session. Reaping it closed the agent's
tool transport, so `tether_receive` failed with **"Transport closed"** even though message
delivery itself was working (the autofire landed; the agent just couldn't resolve the handle).

## The fix

MCP servers are now treated as agent-owned, never dashboard-owned:

- Removed `tether/mcp_server.py` / `tether.mcp_server` from `REAP_MARKERS`.
- Added a hard `REAP_NEVER` exclusion (`mcp_server`) checked before any marker match, so a
  future marker change can't re-introduce the bug.

Reaping still clears the actual sprawl — orphaned `ping_daemon`, `agent_server`, and stale
dashboard processes — without touching the transports the agents depend on.

## Recovery

An agent whose MCP server was already reaped (pre-patch) must reconnect its Tether MCP to
respawn the stdio transport (restart the MCP connection or the agent CLI). After that,
`tether_receive` resolves normally.
